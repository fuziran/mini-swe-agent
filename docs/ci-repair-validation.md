# CI 修复候选的验证规则

本页固定 `mini-ci-repair` 将候选补丁判为 `verified` 的条件。四次测试的 XML 保存及节点级判定已实现，并已用真实临时 Git 仓库、pytest 和 Docker 验证下列候选结果；现有五例的历史报告不按新规则追溯改写。

## 证据与节点

- `F` 是原 CI 输入中的失败 pytest 节点集合，不能为空。原 CI 可用 `pytest.xml`，缺失时沿用当前文本日志回退规则。
- `B1`、`B2` 是原故障提交的两次全量基线，`T` 是补丁后的原失败节点定向测试，`C` 是补丁后的全量测试。四次运行各自保存本次生成的 pytest XML 和文本日志。
- 每个 XML 测试节点按 pytest 路径映射为唯一节点 ID，结果分为 `passed`、`failed`、`error`、`skipped`。Pytest 的预期失败在 XML 中按 `skipped` 处理。节点不能映射或重复时，整个结果记为 `execution_error`。
- XML 必须存在、可解析、包含测试节点，且与进程退出码一致。XML 缺失、损坏、结果矛盾或无法识别时，记为 `execution_error`，不得只根据退出码或日志摘要判为通过。

## 验证顺序

| 阶段 | 必须满足的条件 | 不满足时 |
| --- | --- | --- |
| 首次基线 `B1` | pytest 退出码为 1；XML 中失败节点恰好为 `F`，且没有测试错误。 | 原故障不一致为 `not_reproduced`；结果无效为 `execution_error`。 |
| 重复基线 `B2` | 与 `B1` 的节点集合及逐节点结果相同，仍恰好在 `F` 失败。 | 结果变化为 `unstable`；结果无效为 `execution_error`。 |
| 定向测试 `T` | pytest 退出码为 0；XML 节点集合恰好为 `F`，且每个节点都为 `passed`。 | 测试失败、跳过或节点缺失为 `target_failed`；结果无效为 `execution_error`。 |
| 全量测试 `C` | pytest 退出码为 0；节点集合与 `B1` 完全相同；`F` 中每个节点均为 `passed`；不存在 `B1` 中没有的 `skipped` 节点；其余非跳过节点均为 `passed`。 | 失败、新增跳过、节点新增或消失为 `candidate_failed`；结果无效为 `execution_error`。 |

所有阶段通过且现有补丁范围检查通过后，才可写入 `status=verified` 并允许发布。原有跳过节点可以继续跳过或变为通过；新增测试节点同样拒绝，因为当前修复只允许修改 `src/*.py`，测试清单变化需要人工审查。目标测试和全量测试都要确认 `F` 实际通过，避免全量运行时因条件变化而漏测。

## 报告与验收

`report.json` 保留现有状态、阶段、原因、耗时和可取得的模型调用与费用；另外记录每次运行的节点数、失败及跳过节点，以及候选相对基线新增或消失的节点。拒绝原因要明确指出是失败、跳过、节点变化还是结果无效。四份 XML 与对应日志一并保留，供复核。

现有验证使用真实临时 Git 仓库、pytest 和 Docker 覆盖正常修复、原失败节点被跳过、原失败节点从全量测试消失、其他节点新增跳过，以及 Docker 未产生 XML 的无效结果；未使用 mock/patch。完整入口另用仓库自带的确定性模型验收模型初始化及执行异常、测试文件越界修改、目标失败和全量回归报告；补丁应用失败用真实 Git 冲突验收应用函数及报告映射。此规则证明 pytest 报告的节点执行结果，不能证明测试断言本身足够充分。
